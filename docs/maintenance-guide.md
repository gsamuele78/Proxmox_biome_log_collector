# Maintenance guide

How to change, upgrade and release this repo. It is written for both
people and coding agents; [AGENTS.md](../AGENTS.md) is the short version
for agents. For which test proves what, see [testing.md](testing.md).

## Rules that always apply

1. **The deployed files are the product.** Everything under
   `docker-compose*.yml`, `config/`, `scripts/`, `docker/` and `docs/` gets
   deployed or followed by an operator. A fix found in the lab goes there,
   never only into `tests/lab/`.
2. **Lab-only material never ships.** `tests/lab/lab.env`,
   `tests/lab/docker-compose.lab.yml`, `tests/lab/provision/` and the
   Keycloak realm hold throwaway credentials and lab addresses.
3. **No real values in git.** Real hostnames, IPs, tokens and passwords
   live in the gitignored `.env` and `config/prometheus/targets/*.json` on
   the monitoring VM. `.env.example` and the `*.json.example` files show
   the shape.
4. **Every change lands in `CHANGELOG.md` under `[Unreleased]`**, in the
   right subsection (Added, Changed, Fixed, Removed, Security). If an
   operator has to do something on upgrade, write the steps in the entry.
5. **Architecture changes get an ADR** in `docs/adr/` (template
   `0000-template.md`). A new component, a replaced component or a changed
   trust boundary counts; a version bump doesn't.
6. **Docs follow code in the same commit.** `tests/lint/check-drift.py`
   catches the mechanical cases (alerts, env vars, tags, scripts, links);
   the rest is on the reviewer.

## Where each fact lives

Change the source of truth, then whatever repeats it.

| Fact | Source of truth | Also repeated in |
| --- | --- | --- |
| Image tags | `docker-compose.yml`, `docker-compose.pegaprox.yml` | promtool/amtool tags: `.github/workflows/validate-and-test.yml`, `tests/README.md`, `Makefile`; lab-only tags (Mailpit, Keycloak, curl) in `tests/lab/` and `validate-and-test.yml` |
| cv4pve versions | `ARG CV4PVE_VERSION` / `ARG CV4PVE_DEB_SHA256` in `docker/*/Dockerfile` | image tag in `docker-compose.yml`, `.github/workflows/security-scan.yml` |
| Environment variables | `.env.example` | `docs/deployment-guide.md`, `tests/lab/lab.env`, `tests/integration/smoke-test.sh` |
| Ports and exposure | `docker-compose.yml`, `config/traefik/` | `docs/network-port-matrix.md`, `docs/architecture.md` |
| Alert rules | `config/prometheus/rules/*.yml` | alert catalogue in `docs/runbook-incident-response.md` |
| Scrape jobs | `config/prometheus/prometheus.yml` | `expected_jobs` in `tests/integration/smoke-test.sh`, job list in `tests/e2e/t0-deploy.sh` |
| Hardening baseline | `docs/hardening.md` | every service block in the compose files |
| Release history | `CHANGELOG.md` | GitHub Releases (generated by `release.yml`), README badge |

The drift check enforces the rows about tags, env vars and alerts.

## Common changes

### Bump a container image

1. Change the tag in the compose file. For `prom/prometheus` and
   `prom/alertmanager`, also in the places listed above (the drift check
   fails until you do).
2. Read the upstream release notes between the two versions for config
   or flag changes, and adjust `config/`.
3. CI green, then lab tier 1 (tier 3 for Traefik, oauth2-proxy, Loki).
4. `CHANGELOG.md` → `### Changed`: `` `traefik` v3.7.9 → v3.7.13 ``.

### Bump cv4pve-diag or cv4pve-metrics-exporter

Follow "Updating custom-built images" in
[deployment-guide.md](deployment-guide.md). Also update the image tag in
`docker-compose.yml` and in `.github/workflows/security-scan.yml`, and
re-check the CLI flags used by `scripts/run-cv4pve-diag.sh` and the token
permissions in `.env.example`. The checksum must be verified by a person
against the release page (ADR-0007), never copied from a bot.

### Add or change an alert

1. Edit `config/prometheus/rules/<area>.rules.yml`, with `severity`,
   `summary` and `description`.
2. Add or update the row in the runbook's alert catalogue.
3. `make validate` (promtool checks the rules).
4. For PVE/Ceph alerts, prove it fires in lab tier 2 with a
   `t2-alert.sh` phase in `tests/lab/run.sh`.

### Add an environment variable

1. Use it in the compose file or template.
2. Declare it in `.env.example` with a comment: what it does, the safe
   default, whether it's required.
3. If it's required, add it to `required_vars` in
   `scripts/bootstrap-monitoring-vm.sh`. If it has a default in the
   template, set it in the bootstrap script too (envsubst has no
   `${VAR:-default}`).
4. Add the lab value to `tests/lab/lab.env` and the dummy value to
   `tests/integration/smoke-test.sh`.
5. Write the operator's upgrade step in the changelog entry: an existing
   `.env` won't have the key.

### Add a service

Follow `docs/hardening.md` (pinned tag, dropped capabilities,
`no-new-privileges`, resource limits, healthcheck, no host port unless
required), add it to the healthcheck list in
`tests/integration/smoke-test.sh` and `tests/e2e/lib.sh` (`all_healthy`),
to the scrape config if it exposes metrics, to
`docs/network-port-matrix.md` and `docs/architecture.md`, and write an ADR.

## Release

1. `CHANGELOG.md`: rename `## [Unreleased]` content into
   `## [X.Y.Z] - YYYY-MM-DD` and leave an empty `## [Unreleased]` above it.
   Semantic versioning: an operator action on upgrade (removed/renamed
   variable, new required step) is at least a minor bump before 1.0.
2. Run the lab at the highest tier the release touches, from clean
   (`make lab-destroy`, then `make lab-up TIER=N && make lab-test TIER=N`).
3. Commit `release: X.Y.Z`, then tag and push:

   ```bash
   git tag -a vX.Y.Z -m "X.Y.Z"
   git push && git push --tags
   ```

4. `release.yml` publishes the GitHub Release with the changelog section as
   its notes and fails if the section is missing. The README's release
   badge updates by itself.
5. Check that the four workflows are green on the release commit.

## Upgrade a deployment

On the monitoring VM, as root, in the checkout (`/opt/proxmox-biome`):

1. Read every `CHANGELOG.md` entry between the deployed version
   (`git describe --tags`) and the target, especially "Removed" and any
   upgrade notes. Apply the `.env` changes they list.
2. `git fetch --tags && git checkout vX.Y.Z`
3. `scripts/generate-secrets.sh && scripts/bootstrap-monitoring-vm.sh`
   (both idempotent; they fill new secrets and re-render the templates).
4. If `scripts/systemd/` changed: copy the units again and
   `systemctl daemon-reload`.
5. If `scripts/configure-pdm-firewall.sh` changed: re-run it. Never
   `systemctl restart nftables` on this host (it flushes Docker's rules);
   if it happens, `systemctl restart docker`.
6. If `scripts/node-setup/` changed: re-run the changed scripts on every
   PVE node.
7. Check: `docker compose ps` (all healthy),
   `https://prometheus.<domain>/targets` (all up), the test alert from
   deployment guide step 9.
