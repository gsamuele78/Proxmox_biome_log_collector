# ADR-0006: Local-auth bootstrap first, Keycloak OIDC SSO as the steady state

Status: Accepted
Date: 2026-07-31

## Context

Every exposed surface (Traefik dashboard, Grafana, Prometheus, Alertmanager,
PDM, cv4pve-diag's static reports, optionally PegaProx) needs *some* form of
authentication from day one, but standing up a full Keycloak realm before
the monitoring stack itself can even be validated creates a
chicken-and-egg bootstrapping problem. The requirement is local auth
initially, with Keycloak integration supported thereafter — not
Keycloak-or-nothing.

## Decision

Two-phase auth model:

1. **Phase 1 (bootstrap)**: Traefik's `basicAuth` middleware
   (`config/traefik/dynamic/middlewares.yml`, credentials generated by
   `scripts/generate-secrets.sh` into an htpasswd file) fronts every router
   that doesn't have native auth of its own (Grafana still uses its own
   local admin account underneath, PDM/PVE use their own realm). This is
   enough to deploy and validate the whole stack before any SSO
   infrastructure exists.
2. **Phase 2 (steady state)**: Keycloak OIDC — Grafana's native
   `auth.generic_oauth`, Proxmox VE/PDM's `pveum realm add --type openid`,
   and **oauth2-proxy** as a Traefik ForwardAuth middleware
   (`docker-compose.yml`, profile `keycloak`) for everything with no native
   OIDC support (PDM's web UI redirect flow if not using its own OIDC
   realm config, cv4pve-diag's static HTML reports, optionally PegaProx).
   Documented step-by-step in `docs/keycloak-integration.md`.

Switching a given router from `basic-auth@file` to
`oauth2-proxy-auth@file` in its `middlewares` label is the entire migration
step per service — both middlewares already exist in
`config/traefik/dynamic/middlewares.yml`.

## Consequences

- The stack is deployable and testable (including in CI's smoke test,
  `tests/integration/smoke-test.sh`) without any Keycloak dependency.
- Every surface ends up behind Keycloak SSO/MFA eventually, not just the
  ones with native OIDC support — oauth2-proxy closes that gap for the
  rest.
- Two auth layers stack during the transition period for
  natively-OIDC-aware services (e.g., Grafana's own login screen sits
  behind Traefik's edge auth until the label is flipped) — a deliberate,
  temporary redundancy documented in the migration guide, not a bug.
- `.env.example` carries both the bootstrap `TRAEFIK_BASIC_AUTH_USERS` var
  and the `KEYCLOAK_*`/`OAUTH2_PROXY_*` vars side by side, with the latter
  left blank until Phase 2 is actually undertaken.

## Alternatives considered

- **Keycloak from day one, no local-auth fallback** — rejected: makes
  first boot/validation of the monitoring stack depend on a second piece
  of infrastructure (a working Keycloak realm) existing first, which is a
  worse bootstrapping experience and harder to validate in CI.
- **Permanent local auth, no SSO path** — rejected: doesn't meet the
  stated requirement for Keycloak integration support, and doesn't scale
  to a growing admin team needing centralized MFA/audit trails for access
  to compliance-sensitive surfaces.
